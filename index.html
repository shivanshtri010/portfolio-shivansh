The problem

Manual nutrition logging is friction. The product needed to turn a meal photo into structured data without a human in the loop.

The approach

A Spring Boot API accepts an image, calls a custom YOLOv8 model, maps detections to nutrition data, and returns a structured response the client can render.

Architecture
  • Spring Boot REST endpoints for image upload and nutrition lookup.
  • Custom YOLOv8 model served behind the API, not by the client.
  • Detection-to-nutrition mapping in the backend.
  • JSON responses shaped for the product, not raw model output.
Key decisions
  • Keep inference behind the API, so model changes never break the client.
  • Return structured nutrition, not detections, so the UI can focus on portions and macros.
  • Optimise for predictable latency in a live demo over maximum model size.

The problem

Fixed irrigation schedules waste water and miss crop stress. The system needed field telemetry and guidance grounded in it.

The approach

Sensors publish telemetry over MQTT. Spring Boot APIs ingest and expose it, and a fine-tuned Llama 3 8B model turns the readings into irrigation guidance.

Architecture
  • Soil, flow and temperature sensors publish over MQTT.

Distributed backend 2025

E-Commerce Microservices Platform

A commerce backend split into independent user, product, order and payment services — synchronous where the request needs an answer, event-driven where it does not.

Impact−40%API latency
Scope4domain services
AuthJWT+ RBAC
Request code
System / 03 async path
REST / Kafka / RedisSpring Boot
The problem

Commerce backends tend to start as one deployable. Every change carries the risk of the whole surface, and a slow payment provider can hold up the catalogue.

The approach

Split the domain into independently deployable services, keep synchronous REST for reads and validation, and move order state transitions onto Kafka so downstream work does not hold the request open.

Architecture
  • Spring Boot services for user, product, order and payment.
  • JWT and Spring Security RBAC at the edge of every protected route.
  • MySQL via Hibernate/JPA; Redis cache-aside on read-heavy endpoints.
  • Docker per service, with JUnit coverage around domain logic.
Key decisions
  • Cache-aside over write-through: reads dominate, and seconds-old product data is acceptable.
  • Events over distributed transactions: order state publishes to Kafka instead of spanning services in one transaction.
  • One container recipe per service, so local and CI environments behave the same way.

Task Management REST API

15+ secured endpoints with JWT and role-based access, pagination and filtering at the query layer, and a Redis cache that keeps repeat reads under 100 ms.

Surface15+endpoints

System / 04 secure path
Auth / query / cacheSpring Security
The problem

A task product needs secure access, predictable list performance, and enough test coverage to change the API without fear.

The approach

Fifteen-plus REST endpoints behind JWT authentication and role-based authorization. Pagination and filtering happen in SQL, and repeated reads go through Redis.

Architecture
  • Spring Boot controllers with a Spring Security filter chain.
  • MySQL persistence, with pagination and filtering pushed into queries.
  • Redis cache-aside for repeated reads.
  • JUnit suite covering endpoint and authorization behaviour.
Key decisions
  • Authorize at the filter chain, not in every controller.
  • Paginate and filter in SQL; never load a table and trim it in memory.
  • Cache reads, not writes, with invalidation close to the write path.

“Good systems feel inevitable. The best compliment a backend can get is silence.”

I'm Shivansh, a software engineer in Noida. I build Java services at Info Edge (NaukriGulf), where the work ranges from CRUD APIs and MySQL schemas to an LLM-backed validation service that catches inconsistencies across job content.

I came to software through engineering school and a lot of self-directed building. That route is probably why I think about systems in terms of signals, feedback and failure modes — and why I care as much about what happens when a service is slow as when it is fast.

My favourite problems sit where correctness meets scale: a cache that removes a second from every request, an event stream that keeps orders moving when a consumer falls behind, a model that earns its place in the product instead of the demo. I like the unglamorous parts — clear boundaries, explicit errors, tests that fail for the right reason, and dashboards that tell the truth at 2 a.m.

01

Own the whole path.

Design, build, test, deploy, support. The feedback loop is the job — not a handoff.

02

Make failure explicit.

Happy paths are easy. I spend my time on timeouts, retries, partial failures, and what the logs say when it breaks.

03

Measure the outcome.

Latency, coverage, hours saved. If it cannot be measured, it is still a hypothesis.
